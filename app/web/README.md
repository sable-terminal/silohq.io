# Silo web client

The browser client of a Silo cell (spec Parts V and VI). It is built in stages: W1 holds the foundation, sign-in and the workspace shell (decision D138 in `docs/siloDatabaseDesign.doc.md`); W2, Home's briefing, following and the notifications panel (D139); W3, Explorer and Cmd-K's search (D140).

## How it is built and served

- **Static export.** Next.js (`output: 'export'`) builds plain files into `out/`. There is no server of its own, and the same files serve hosted and self-managed cells.
- **Served by the gateway.** The cell's gateway serves `out/` at its public origin, beside the API under `/api/v1`. Set `GATEWAY_WEB_ROOT` to the `out` directory.
- **Same origin.** Pages and API share the origin. The session is the gateway's `__Host-` cookie, `SameSite=Strict`, which page script never reads.
- **Strict CSP.** Each page's Content-Security-Policy allows only its own inline scripts, by hash. Nothing inline besides them runs, and no style attributes are used.
- **Rendered in the browser.** Pages carry no data: everything they show comes through the API, under the session.
- **Ids in the query string.** A static export has no page for an id it did not know at build time, so an object's id travels as a query parameter.
- **System fonts only.** Nothing is fetched from outside the cell, which matters for air-gapped deployments.
- **No telemetry.** Next.js telemetry is off in every script.

## Calls to the API

- `src/api/client.ts` calls the public API.
- **Typed by the server's routes.** Types come from the gateway's route definitions (`app/server/src/contracts/gateway`) through type-only imports, so no server code reaches the bundle.
- **Generated route table.** `src/api/routes.generated.ts` is generated by the server: `node src/scripts/webRoutes.script.ts` in `app/server`. Regenerate it after changing a public route; tests in both projects fail until it is current.
- **What the client sends:**
  - `x-silo-csrf` on every state-changing call;
  - an `Idempotency-Key` on keyed calls, reused for retries of one intent.
- **Refusals** carry the gateway's own message, category, code and correlation id.

## Layout

| Path | Holds |
|---|---|
| `src/app/` | Pages (App Router). `sign-in/`, `sso/callback/` and `sso/complete/` stand alone; `(shell)/` holds every page inside the workspace shell. |
| `src/explorer/` | Explorer (spec 34.1): the vocabulary, its plans (values as parameters; filters as a saved set's predicate), facets, the object table, search results. |
| `src/shell/` | The shell (spec 33.2): rail, top bar, Cmd-K palette, identity menu, Ask panel, status line, and the context every page reads. |
| `src/api/` | The API client and the generated route table. |
| `src/ui/` | Shared styles and small components. |
| `src/lib/` | Navigation guards and the theme. |
| `tests/` | `node:test` suites: the API client, the contrast of the design tokens, and the browser test. |

## Commands

```sh
npm install
npm run build       # writes out/
npm run typecheck   # TypeScript 7, as the server
npm test            # API client, contrast, and the browser test
```

The browser test builds the export and starts a cell of real services from the server's test helpers. It needs:
- the local stack (`npm run db:up` and `npm run infra:up` in `app/server`);
- an installed Chrome, which it drives headless through `playwright-core` (no browser is downloaded; set `CHROME_PATH` for another location).

It skips where either is missing. Set `SCREENSHOTS_DIR` to keep screenshots of the pages it visits.

## Accessibility

Design tokens meet WCAG 2.2 AA in the light and dark themes (`tests/contrast.test.ts` checks every pair). The theme follows the device unless the person picks one, and reduced motion is honoured.

Every control has a visible label or an accessible name. Rail items the person may not use are `aria-disabled` buttons that name the permission they need (spec 33.3).
