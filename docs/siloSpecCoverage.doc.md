# Silo specification coverage

Checked on 3 November 2026 against the master specification of 28 October 2026, after the
Siloes Capture and Import services were built, and brought up to date on 4 November after
tenant migrations and the organisation export, and on 7 November after the AI FDE and the admin portal. On 24 November the chapters still marked partial were checked again: none names a gap the specification requires, so all are now built. It answers one question: what of the
specification is built in `app/server`, and what is not.

## Summary

- **Scope of this repository.** It holds the server (app/server), the Silo Agent (agent/,
  chapter 10) and the web client (app/web, built in stages from 2026-11-17, D138 onwards:
  sign-in and the shell, Cmd-K, Explorer, object views, Ask and dashboards, Governance, Connect,
  Ontology, Studio, Scenarios, Files, Siloes, Settings and the Clone Canvas in every layout,
  3D included). Compliance (chapter 65) is not code.
- **Services.** All 61 server services in the catalogue are built. The 62nd, `silo-agent`, is a separate
  program and not in this repository.
- **Checked mechanically.**

  | Check | Result |
  |---|---|
  | Permission catalogue (76) | All 141 permissions are seeded: the spec's, less connector.promote and connector.tier_promote, the marketplace's, dropped on 2026-11-23 (D224), and workbook.save, report.save, process.save, pipeline.save, ai_agent.save, notebook.save and model.save, beyond the spec (D232 to D240). |
  | Data model index (78) | Every table exists, except the BigQuery Action ledger (created in each Warehouse's dataset, not in Postgres; the sovereign cell's is `siloes.action_ledger`, D205) and three tables the design doc renamed by decision. |
  | Audit event catalogue (77) | Every event chapter 77 lists is raised, or settled by decision (D207, 22 November). On 10 November 132 of 578 were raised by no service; the lists below record that check as it stood then. |
  | Reachability (invariant 12) | Of 488 service endpoints, 55 had no caller; after the fixes below, 35 do. With tenant-migrations built, its two directory endpoints have a caller and its five operator endpoints waited for admin-portal, so 38 did. With admin-portal built, 27 of those have their caller, leaving 11: five waited for the cell-side Fleet agent, and six for a caller that does not call yet or works in process. With the Fleet agent built (D196 to D200), five remained: the PNG renderer's three, which waited for the web client, and the expression evaluator's two. With PNG drawn by the exporter's own browser (D225), two remain: the expression evaluator's, whose callers evaluate in process. This is a build check (`tests/architecture/reachability.test.ts`), with each known case listed and explained. |

- **Gaps in phase 1, the product's core, found by this check and now fixed:**
  - OAuth connections, and managing a connection after it is created (its secrets, parameters, status moves and conformance runs), had no public routes. They do now.
  - New members had no way to receive a seat, so they got no allowance and no 200-token onboarding grant. Seats are now built (72).
  - Organisations were not registered with the directory when provisioned. They are now.

  - The 3D view is phase 9, not the first release.
  - AI FDE stage exits: the AI proposes each with its evidence; the customer's named engagement owner confirms it; a stage that writes to source systems needs a confirmer holding the Action permission; Silo staff confirm nothing.

- Chapter 43.7 says the walk "follows ontology links, so a dependency between two systems with no shared foreign key is still reported". The entity graph holds keyed hashes, not identifiers, so it cannot name the deleted record's counterpart in the other system; the walk finds it as resolution matches records, by the type's match keys in order, read there by the key's mapped field (normalisation not applied), and reports the records holding the counterpart's key. A link that cannot be followed leaves the walk bounded. Hop 1 only.
- Chapter 52.3 says band thresholds are per kind, set from measured acceptance, but not which acceptance makes a band. This build: high starts at the lowest confidence above which nine in ten of the organisation's decided proposals of the kind were accepted unchanged, medium where six in ten were accepted at all, each with at least ten decisions and the kind at least twenty; until then 0.85 and 0.6 hold.
- Chapter 48.1 says prior state is read by key in the write's own transaction "where the warehouse supports it". The agent runs a plan as one round trip, so Silo guards each update and delete with the prior state it recorded, compared null-safely in the same statement: a row changed since matches nothing and the plan rolls back as a conflict (`write.prior_changed`). SQL Server and Oracle (no null-safe comparison generated) and JSON fields go unguarded; the stale re-read before the plan still covers them.
- Chapter 42.5 says that where only `update_full` exists every field it sends is touched prior state. A full update sends every field but the identifier (the write is refused if one is missing), the proposer must be able to read every field, and every mapped property counts as touched for marking-conditioned approval policies. An upsert names its record, so an Action type creating through one must give the identifier a value; the record is read first and is prior state when it exists, and revert deletes it or restores it accordingly.
- Chapter 42.8 gives `state_only` for "custom actions with no compensating endpoint". Restoring their fields needs the manifest's update; where none is declared the revert is refused, and the type should be compensating.
- Chapter 44.3 applies a marking condition "when the mutation touches a marked field". This build counts the markings its receipt inherits (58.6): on the Action type, the object type, the properties written, the source fields those properties map (D67) and the connections written. Policy resolves source-field markings for reads too.
- Chapter 48.3 says Action events travel on the durable bus and are delivered by notify, but not what happens to events while a subscription is paused. This build offers a paused subscription nothing new, and its pending deliveries wait for it to resume.
- Chapter 48.2 says the actions service writes the ledger rows after the receipt. It sends them to warehouse-sync, which writes BigQuery; a copy still failing after three tries is kept, its rows sealed to it, and sent again (a minute, doubling to six hours) until written (D223). The rows name the object type by id.
- Chapter 30.8 reads a past value "as observed at" a time. Capture keeps changes and when each object was first seen, so a value is shown observed when it began (its change, or the first sighting), not the last time it was seen unchanged.
- Chapter 40.5 lets a Cron mutate the objects its question returns but does not say how they are named or where parameter values come from. This build names them by the key of a single-source type the question selects, and takes Action types that need no parameter value, since a Cron stores no values. Execute within bounds writes property updates and creates only; a delete, a link or a custom action is proposed instead. With separated execution, an execute-within-bounds mutation still waits for a person to run it.
- Chapter 29.10 exports a canvas as PNG or PDF. This build exports both: PDF drawn as vectors with standard fonts, and PNG drawn by the exporter's own browser (D225), maps with their base map (D227) and the 3D view with its model (D228).
- Chapter 21.8 stores one key pair per route, but a junction object has two. This build reads a many-to-many route as the junction's key to the route's source object (its foreign key field and referenced field) and takes the junction's key to the other side from the relationship the junction's manifest declares to that side's object; a junction declaring none cannot be followed, and the plan says so.
- Chapter 58.9 calls a declassification an Action (chapter 42), but an `action.mutations` row writes source records of an object type, which a declassification does not. This build makes it its own governed record (`gov.marking_declassifications`, `action_id` its own id) with an approval chain of its own subject kind: previewed, approved by another person who satisfies the marking, audited and revertible, as 58.9 requires (D62).
- Chapter 39.8 applies a staged Action's effect and walks "downstream consequences" with the rules of 39.4, which propagate failure and delay. This build maps an effect into those terms: a delete makes its target unavailable, a date or instant moved later delays it by the largest move, and any other change propagates nothing, which the branch states.
- Chapter 45.4 makes the canary sample "configurable per organisation" but gives no setting for it. This build keeps it as an organisation setting (D66: 1 to 9,999 rows, 100 by default), set by a holder of mutation.policy.

- Chapter 25.8 says a rollback's content "equals a named prior version". It does, element for element, except each restored object type's `typeVersionId`: the rollback writes new type version rows, so lineage records a new version. - Chapter 22.3 says a distinct count is "exact where the source pushes COUNT(DISTINCT); otherwise null". This build also gives it when every row of the object was examined (the bounded read reached the end), since the count is then exact, not estimated.
